# 429 amplification: retry-after backoff and singleflight

Issue: https://github.com/gnoverse/gnoscope/issues/525 (parts 1 and 2 only)
PR: https://github.com/gnoverse/gnoscope/pull/526
Branch: `ws/d-20261123-gnoscope429`
Commits: `9de01ce`, `46a4234`

## Which retry-after source actually carries the hint on this upstream

**The body.** Both are read, header first, and the asymmetry in the evidence is
the reason both are read rather than one.

The captured production line is

```
indexer returned 429 Too Many Requests:
{"code":-32000,"message":"Per-IP rate limit exceeded; retry after 300 seconds."}
```

That line is printed by `doQuery`, which formats `resp.Status` and the first 200
bytes of the body and never looks at `resp.Header`. So the log proves the number
is in the body, and proves nothing either way about whether a `Retry-After`
header was also present. I did not probe `indexer.onyx.testnets.gno.land` to
find out, because the only way to see a 429's headers is to earn a 429, and
deliberately tripping a production per-IP limit to confirm a detail that does
not change the implementation is not a trade worth making.

So `newRateLimitError` reads the header first (RFC 9110 delta-seconds and
HTTP-date), falls back to scanning the body, and records which one answered in
`RateLimitError.RetryAfterSource`. An upstream that grows a header later is
honoured with no further change; the one we have today is honoured now.

The body scan is a regex over the message text, not a decode, because the number
is prose inside a JSON-RPC-shaped envelope rather than a field. It matches
`retry after/in N`, `try again in N`, `wait N`, with optional `ms` / `s` /
`minutes` units, defaulting to seconds. Matching loosely is the right trade: a
false positive costs one over-long pause, a miss costs the 60-second retry loop
this whole change exists to stop.

## The singleflight choice and why

**`golang.org/x/sync/singleflight`.**

- It was already in `go.sum` (`v0.19.0`, with the module zip hash, so already in
  the verified module graph) and already in the local module cache. Promoting it
  from the graph to a direct require adds no new supply chain surface.
- It is maintained by the Go team and is the canonical implementation.
- An internal version is roughly sixty lines of subtle concurrency (the
  `dup`/`forgotten` bookkeeping, panic propagation, `DoChan`) to own forever for
  no gain, in a repo whose `go.mod` has exactly two direct dependencies and
  clearly intends to keep that number honest.

`DoChan` rather than `Do`, so each caller can select on its own context while
the shared round trip runs under one detached from any single caller.

The key is `url + "\x00" + body`, where `body` is the exact bytes that would go
on the wire. `encoding/json` sorts map keys, so the serialised vars are stable
regardless of insertion order. The endpoint is in the key because the pool fails
over and two endpoints are two chains' worth of different questions.

No TTL cache, on purpose, and `TestCollapsingIsInFlightOnlyAndCachesNothing`
pins it: three sequential calls are still three requests.

## What shipped

New: `pkg/indexer/ratelimit.go` (`ErrRateLimited`, `RateLimitError`,
`RetryAfterOf`, `RateLimitPause`, both parsers).

Changed:
- `pkg/indexer/indexer.go`: a 429 is typed rather than a generic transport
  error; `doQuery` split into a decoding half and a shared `fetch`;
  `recordResult` shuts the breaker on the first refusal, for the server's
  number, doubling with jitter; `pauseUntil` extends and never shortens;
  `PausedUntil` exported.
- `pkg/httpapi/api.go`, `api_chain.go`: the same two rules on the per-network
  `healthTracker`, using the same `indexer.RateLimitPause`.
- `pkg/syncer/syncer.go`: `SyncAll` returns immediately while the breaker is
  shut, instead of letting eighteen passes each discover it.
- `pkg/indexer/fake.go`: `StatusBody`, `StatusHeader`, `QueryCount`.
- `docs/architecture.md`.

Tests: `pkg/indexer/ratelimit_test.go`, `pkg/indexer/singleflight_test.go`,
`pkg/httpapi/health_ratelimit_test.go`, `pkg/syncer/ratelimit_test.go`.

A security hook caught two real defects in the first commit, both fixed in
`46a4234` and both pinned by tests I confirmed fail against the pre-fix code:
the shared round trip inherited the starting caller's cancellation, and the
backoff ladder advanced once per collapsed caller rather than once per round
trip (six readers on one 429 jumped straight to the 15 minute ceiling).

## Places that bypass the breaker, found and NOT fixed

Named, not quietly left. Every one of these goes through `indexer.Client.query`,
so the **client** breaker now stands them down for the server's number, which is
where the amplification measured in the issue actually lived. What they bypass
is the HTTP layer's per-network `healthTracker`, which only `fanOut` feeds.

1. **Single-network handlers calling `a.clientFor(network)` directly.** They
   neither call `health.shouldSkip` before asking nor `health.record` after, so
   a network refusing every request never shows up in the tracker that the
   merged pages consult:
   - `pkg/httpapi/api_chain.go:152, 237, 460, 543, 567, 633, 709`
   - `pkg/httpapi/api_packages.go:476, 522, 539, 624`
   - `pkg/httpapi/api_analytics.go:30, 275, 301`
   - `pkg/httpapi/params.go:498`
   - `pkg/httpapi/api_storagemap.go:175`
   - `pkg/httpapi/govdao_provenance.go:57`
   - `pkg/httpapi/assets.go:161`
   - `pkg/httpapi/mcp.go:645`
2. **`pkg/httpapi/ws.go`, the SSE live feed.** `pollLoop` runs its own ticker
   per network against the serve client and never reports to `healthTracker`
   either. Same shape as (1), listed separately because it is a background
   loop rather than a request handler, so nobody's page load pays for it and
   nobody notices it asking.
3. **`pkg/httpapi/chainhealth.go`, `probeNode`.** Hits the RPC endpoint with its
   own `http.Client`, not the indexer pool, so neither breaker applies. Correct
   as it stands (a health probe that stops probing when things are unhealthy is
   useless), recorded because it is a real path to an upstream that no breaker
   covers.
4. **The client breaker is per pool, not per endpoint.** A 429 from one member
   pauses the whole pool including a healthy sibling. Pre-existing for every
   error kind; this change inherits it rather than introducing it.
5. **A 429 still triggers failover to the next endpoint** before the breaker
   shuts, because `answered()` does not recognise `ErrRateLimited`. Left
   deliberately: a different host has a different per-IP budget, and trying it
   is the entire point of a pool.
6. **No token bucket between the syncer and the reader.** They share one per-IP
   allowance with nothing arbitrating, so a sync pass can still spend the whole
   budget before a page asks. That is part 3 of the issue and is out of scope
   here.
